# CLI

The `pandora` command exposes each component as a subcommand: `fetch`, `ingest`, `canonicalise`, `curate`, `dedup`, `similarity`, `cluster`, `partition`, `annotate`, `manifest`, `reproduce`, `export`. Run `pandora <subcommand> -h` for its arguments, or `pandora -h` for the full list.

`fetch` downloads from PDBe/PDB; `ingest` instead lists mmCIF files you already have on disk (e.g. a local bulk PDB mirror or the PDBe release tree) by `--glob` or `--path-template` — it doesn't download, copy or open anything.

Structure-transforming stages (`canonicalise`, `curate`, `dedup`) write mmCIF files in the PDB archive layout (`<mid>/<entry>.cif`); every stage that reads structures accepts a flat folder, that layout, or a step folder (`<dir>/structures/`). `canonicalise` and `curate` write a step folder: the structures in `structures/<mid>/<entry>.cif` (the PDB archive layout), one row per entry in `entries.<fmt>`, `failures.jsonl` for inputs that raised (the run carries on), and a step summary (`canonicalisation.json` / `curation.json`) recording the policy, Pandora and gemmi versions, input and counts. Tables are Parquet by default; `--table-format jsonl` writes JSON Lines instead (no `export` extra needed, readable with `jq`). A table with no rows is not written. Both refuse an `--output-dir` that already holds step outputs; `--overwrite` replaces them (other files in the folder are left alone). Output files are named by the parsed entry ID, whatever the input file is called (`.cif.gz` inputs are read directly). A second input with the same entry ID is skipped and recorded in `failures.jsonl` as `DuplicateEntry`. For other folder layouts (e.g. the PDBe release tree, `entry/00/100d/clean_mmcif/100d_updated.cif.gz`), list the files with `pandora ingest` and pass its `entries.txt` to `canonicalise --entries`. `ingest` writes `entries.txt` (one absolute path per line) and an `ingestion.json` step summary, without opening any file; `canonicalise --entries` records that summary as its `previous_summary`. `fetch` also writes an `entries.txt` of the files it saved. `canonicalise` also writes `chain_copies.<fmt>` and `mappings.jsonl` (the original-to-canonical ID mappings, one line per entry); `curate` also writes `chains.<fmt>` and `exclusions.<fmt>`, and its summary's `previous_summary` points to the canonicalise summary it read. Other provenance-producing stages write one JSON file per stage into their `--output`/`--output-dir` (e.g. `ingestion_provenance.json`), which `manifest` reads back in; `manifest` takes the step folders with `--canonicalisation-dir` and `--curation-dir`.

`similarity` is a group. `similarity search --engine {mmseqs2,foldseek}` runs an all-vs-all search over a step folder's chains (MMseqs2 reads sequences from `--structures-dir`'s `chains` table, leaving symmetry copies out; Foldseek searches the `{entry}_{chain}.cif` files in `--input-dir`) and writes a similarity layer folder: `layer.parquet`, `unmatched.parquet` and a `layer.json` step summary; `--max-seqs`/`--exhaustive-search` control how many hits are kept. `similarity import` takes an edge list (Parquet, or TSV with a header row) in the `similarity` template (`item_id_1`, `item_id_2`, `score`, ...), with a `--description` YAML that sets `items: entry|chain|interface`; entry and chain items are checked against `--structures-dir`'s `entries`/`chains` tables, interface items against a `residue_contacts` layer given with `--contacts`. Similarity layers are Parquet only (the `export` extra). `cluster --similarity <layer folder>` clusters any similarity layer, with the items from `--structures-dir` or `--contacts` (items with no hits are single-item clusters); `--items entry` on a chain layer clusters entries instead; symmetry copies join their source chain's cluster. It filters hits with `--hit-filter <yaml>` and/or `--min-score`/`--min-coverage` (at least one is required), takes `--contacts` with `--structures-dir` on a chain layer for interface-coverage filters, and `--pairs <path>` (a JSON array of `[item_id_1, item_id_2]` pairs) to derive a paired cluster key per pair, written to `cluster_pairs.json` next to `--output`. See `docs/usage/similarity.md`.

`annotate compute --layer {chain_interfaces,ligand_contacts}` computes one of Pandora's contact layers for every structure of `--structures-dir` and writes the same layer folder as `annotate import` (`layer.<fmt>` of `residue_contacts` rows and a `layer.json` step summary recording the settings); settings are flags (`--distance-cutoff`, `--atom-set`, `--polymer-types`, `--include-waters`), and a flag that doesn't apply to the chosen layer is an error. `annotate import` takes a table from an external tool, converted into one of the layer templates (`residue_contacts`, `residue_values`, `residue_labels`, `chain_values`, `chain_labels`, `interface_labels`, `free_form`), with a `--description` YAML (name, template, tool, version, parameters), and links each row to the structures of `--structures-dir`. Rows may use Pandora's naming (`chain_id`, `seq_id`) or the author's (`auth_chain_id`, `auth_seq_id`, `ins_code`). It writes `layer.<fmt>` (matched rows, both namings filled in), `unmatched.<fmt>` (with a `reason`), `source/` (`--source-files`, copied as-is) and a `layer.json` step summary. Unmatched rows don't stop the run; a table missing a required column does, before anything is written. `annotate count-contacts --contacts <layer folder> --level {residue,chain}` reads a `residue_contacts` layer folder (never structures) and writes a `residue_values` or `chain_values` layer folder of contact counts (`layer.<fmt>`, `layer.json` with `previous_summary` = the contact layer's `layer.json`). See `docs/usage/annotation.md`.
