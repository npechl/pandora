# CLI

The `pandora` command exposes each component as a subcommand: `fetch`, `ingest`, `canonicalise`, `curate`, `dedup`, `similarity`, `cluster`, `representatives`, `rebalance`, `negatives`, `partition`, `annotate`, `manifest`, `reproduce`, `export`. Run `pandora <subcommand> -h` for its arguments, or `pandora -h` for the full list.

`fetch` downloads from PDBe/PDB; `ingest` instead lists mmCIF files you already have on disk (e.g. a local bulk PDB mirror or the PDBe release tree) by `--glob` or `--path-template` — it doesn't download, copy or open anything.

Structure-transforming stages (`canonicalise`, `curate`, `dedup`) write mmCIF files in the PDB archive layout (`<mid>/<entry>.cif`); every stage that reads structures accepts a flat folder, that layout, or a step folder (`<dir>/structures/`). `canonicalise` and `curate` write a step folder: the structures in `structures/<mid>/<entry>.cif` (the PDB archive layout), one row per entry in `entries.<fmt>`, `failures.jsonl` for inputs that raised (the run carries on), and a step summary (`canonicalisation.json` / `curation.json`) recording the policy, Pandora and gemmi versions, input and counts. Tables are Parquet by default; `--table-format jsonl` writes JSON Lines instead (no `export` extra needed, readable with `jq`). A table with no rows is not written. Both refuse an `--output-dir` that already holds step outputs; `--overwrite` replaces them (other files in the folder are left alone). Output files are named by the parsed entry ID, whatever the input file is called (`.cif.gz` inputs are read directly). A second input with the same entry ID is skipped and recorded in `failures.jsonl` as `DuplicateEntry`. For other folder layouts (e.g. the PDBe release tree, `entry/00/100d/clean_mmcif/100d_updated.cif.gz`), list the files with `pandora ingest` and pass its `entries.txt` to `canonicalise --entries`. `ingest` writes `entries.txt` (one absolute path per line) and an `ingestion.json` step summary, without opening any file; `canonicalise --entries` records that summary as its `previous_summary`. `fetch` also writes an `entries.txt` of the files it saved. `canonicalise` also writes `chain_copies.<fmt>` and `mappings.jsonl` (the original-to-canonical ID mappings, one line per entry); `curate` also writes `chains.<fmt>` and `exclusions.<fmt>`, and its summary's `previous_summary` points to the canonicalise summary it read. Other provenance-producing stages write one JSON file per stage into their `--output`/`--output-dir` (e.g. `ingestion_provenance.json`), which `manifest` reads back in; `manifest` takes the step folders with `--canonicalisation-dir` and `--curation-dir`.

`similarity` is a group. `similarity search --engine {mmseqs2,foldseek}` runs an all-vs-all search over a step folder's chains (MMseqs2 reads sequences from `--structures-dir`'s `chains` table, leaving symmetry copies out; Foldseek searches one mmCIF per chain that Pandora cuts from `--structures-dir` itself, symmetry copies left out, or the `{entry}_{chain}.cif` files in `--input-dir`; `--chains <file>` limits either engine to the listed chain item ids, and can't be combined with `--input-dir`) and writes a similarity layer folder: `layer.parquet`, `unmatched.parquet` and a `layer.json` step summary; `--max-seqs`/`--exhaustive-search` control how many hits are kept. `similarity import` takes an edge list (Parquet, or TSV with a header row) in the `similarity` template (`item_id_1`, `item_id_2`, `score`, ...), with a `--description` YAML that sets `items: entry|chain|interface`; entry and chain items are checked against `--structures-dir`'s `entries`/`chains` tables, interface items against a `residue_contacts` layer given with `--contacts`. Similarity layers are Parquet only (the `export` extra). `cluster --similarity <layer folder>` clusters any similarity layer, with the items from `--structures-dir` or `--contacts` (items with no hits are single-item clusters); `--items entry` on a chain layer clusters entries instead; symmetry copies join their source chain's cluster. It filters hits with `--hit-filter <yaml>` and/or `--min-score`/`--min-coverage` (at least one is required), takes `--contacts` with `--structures-dir` on a chain layer for interface-coverage filters, `--chain-representatives <representatives.json>` (with `--items interface`) to map each chain to its representative before rolling chain layers up to interfaces, and `--pairs <path>` (a JSON array of `[item_id_1, item_id_2]` pairs) to derive a paired cluster key per pair, written to `cluster_pairs.json` next to `--output`. See `docs/usage/similarity.md`.

`dedup --contained --clusters <clusters.json>` removes entries contained in another (every cluster has at least as many of the other entry's chains; equal counts keep the best by `DeduplicationRules.contained_rank`, default lowest resolution) and writes a step folder: the kept `structures/`, `entries`, `chains`, `contained` (removed entry → a kept entry containing it), `failures.jsonl` and a `dedup.json` summary. `representatives --clusters <clusters.json> --structures-dir <step folder>` limits the clusters to the folder's chains and picks one per cluster by a `RepresentativePolicy` (default: fewest missing residues, then most hits in the cluster via `--similarity`, then lowest id; symmetry copies are never picked; `--items interface --contacts <layer folder>` instead limits interface clusters to a contact layer and ranks dimers by most residues in contact, best resolution, fewest missing residues, never picking a dimer with a copy chain), writing a JSON list of `{representative, members, n_members}` and `representatives_provenance.json` next to `--output`.

`rebalance --clusters <dimer groups> --contacts <layer folder> --chain-clusters <clusters.json> --similarity ...` picks the positive dimers of each group (one homomer per homomer-only group; otherwise mutually dissimilar heteromers, least connected first, ties by a `RepresentativePolicy` `--policy`) over the dimer graph rebuilt from the same layers, hit filters and `--chain-representatives` as the `cluster` run, and writes a step folder: `positives`, `dropped` (with a `reason`) and a `rebalance.json` summary. `negatives --positives <rebalance folder> --representatives <representatives.json> --similarity <chain layer> --contacts <any-contact layer> --seed N` draws one negative chain pair per positive, avoiding A's structural lookalikes, their binders and the binders' lookalikes, and writes `negatives` and a `negatives.json` summary (seed, counts, unpaired positives). See `docs/usage/similarity.md`.

`partition --clusters <json>` splits whole clusters into train/val/test; `--labels <layer folder>` (a `chain_labels` or `interface_labels` layer) places clusters so every label reaches every split where keeping clusters whole allows, records `label_counts` / `missing_labels` / `labels_layer` in `partition_provenance.json`, prints the unlabelled count and warns for each split missing a label. See `docs/usage/similarity.md`.

`annotate compute --layer {chain_interfaces,ligand_contacts}` computes one of Pandora's contact layers for every structure of `--structures-dir` and writes the same layer folder as `annotate import` (`layer.<fmt>` of `residue_contacts` rows and a `layer.json` step summary recording the settings); settings are flags (`--distance-cutoff`, `--atom-set`, `--polymer-types`, `--include-waters`), and a flag that doesn't apply to the chosen layer is an error. `annotate import` takes a table from an external tool, converted into one of the layer templates (`residue_contacts`, `residue_values`, `residue_labels`, `chain_values`, `chain_labels`, `interface_labels`, `free_form`), with a `--description` YAML (name, template, tool, version, parameters), and links each row to the structures of `--structures-dir`. Rows may use Pandora's naming (`chain_id`, `seq_id`) or the author's (`auth_chain_id`, `auth_seq_id`, `ins_code`). It writes `layer.<fmt>` (matched rows, both namings filled in), `unmatched.<fmt>` (with a `reason`), `source/` (`--source-files`, copied as-is) and a `layer.json` step summary. Unmatched rows don't stop the run; a table missing a required column does, before anything is written. `annotate count-contacts --contacts <layer folder> --level {residue,chain}` reads a `residue_contacts` layer folder (never structures) and writes a `residue_values` or `chain_values` layer folder of contact counts (`layer.<fmt>`, `layer.json` with `previous_summary` = the contact layer's `layer.json`). `annotate label-interfaces --contacts <layer folder> [--min-residues-per-chain N] [--max-total-residues N]` writes an `interface_labels` layer folder with one row per chain pair: residues in contact on each side (`residues_1`, `residues_2`), sequence lengths (`length_1`, `length_2`, `total_residues`, from the `seqres_length` of the `chains` table that `pandora curate` wrote in the structures folder the contact layer traces to) and a `label`: `too_large`, else `few_contacts`, else `ok`; a threshold left out turns its rule off. `annotate interface-gaps --contacts <layer folder>` writes an `interface_labels` layer folder with one row per chain pair: the missing SEQRES positions (incomplete backbone) inside each side's span of non-missing interface residues (`gaps_1`, `gaps_2`, None if the chain can't be measured, read from the structures folder the contact layer traces to) and a `label`: `interface_gap`, else `unknown`, else `ok`. `annotate filter-contacts --contacts <layer folder> --labels <layer folder> --drop <label>` writes a new `residue_contacts` layer folder without the interfaces the `interface_labels` layer marks with a `--drop` label (repeatable); unlabelled interfaces are kept, and the two layers must trace back to the same structures folder. See `docs/usage/annotation.md`.
