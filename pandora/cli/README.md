# CLI

The `pandora` command exposes each component as a subcommand: `fetch`, `ingest`, `canonicalise`, `curate`, `dedup`, `similarity`, `cluster`, `partition`, `annotate`, `manifest`, `reproduce`, `export`. Run `pandora <subcommand> -h` for its arguments, or `pandora -h` for the full list.

`fetch` downloads from PDBe/PDB; `ingest` instead records the same shape of `ingestion_provenance.json` for mmCIF files you already have on disk (e.g. a local bulk PDB mirror) — it doesn't download or copy anything, just describes what's already there.

Structure-transforming stages (`canonicalise`, `curate`, `dedup`) write mmCIF files in the PDB archive layout (`<mid>/<entry>.cif`); every stage that reads structures accepts a flat folder, that layout, or a step folder (`<dir>/structures/`). `canonicalise` and `curate` write a step folder: the structures in `structures/<mid>/<entry>.cif` (the PDB archive layout), one row per entry in `entries.<fmt>`, `failures.jsonl` for inputs that raised (the run carries on), and a step summary (`canonicalisation.json` / `curation.json`) recording the policy, Pandora and gemmi versions, input and counts. Tables are Parquet by default; `--table-format jsonl` writes JSON Lines instead (no `export` extra needed, readable with `jq`). A table with no rows is not written. Both refuse an `--output-dir` that already holds step outputs; `--overwrite` replaces them (other files in the folder are left alone). A second input with the same file name is skipped and recorded in `failures.jsonl` as `DuplicateStem`. `canonicalise` also writes `chain_copies.<fmt>` and `mappings.jsonl` (the original-to-canonical ID mappings, one line per entry); `curate` also writes `chains.<fmt>` and `exclusions.<fmt>`, and its summary's `previous_summary` points to the canonicalise summary it read. Other provenance-producing stages write one JSON file per stage into their `--output`/`--output-dir` (e.g. `ingestion_provenance.json`), which `manifest` reads back in; `manifest` takes the step folders with `--canonicalisation-dir` and `--curation-dir`.

`similarity` writes the tool's hit TSV to `--output` and its `SimilaritySearch` record to `<output>.search.json`; `--max-seqs`/`--exhaustive-search` control how many hits are kept, and `--precomputed-hits <path>` wraps a TSV you ran yourself instead of searching. `cluster` reads that record with `--search`, filters hits with `--hit-filter <yaml>` and/or `--min-score`/`--min-coverage` (at least one is required), takes `--interface-residues <path>` (a JSON `{item_id: [residue position, ...]}` file) for interface-coverage filters, and `--pairs <path>` (a JSON array of `[item_id_1, item_id_2]` pairs) to derive a paired cluster key per pair, written to `cluster_pairs.json` next to `--output`. See `docs/usage/similarity.md`.
